# How CandidCue updates

**Decision: CandidCue 1.0 updates manually. There is no updater.**

This document exists so that the decision is written down somewhere a future
change has to read before switching it. Everything below is the *current*
behaviour, not a plan.

## What the app does

Nothing. CandidCue never contacts an update service, on launch or otherwise.
The only network request the application makes at all is the speech-model
download the user starts from **Settings › Speech**, and that request is
digest-pinned against `scripts/model-catalogue.mjs`.

**Settings › Data, privacy & updates** states the running version — read from
the signed bundle by the `app_version` command — and says how to get a newer
one. That sentence is generated by `describeUpdatePolicy` in
`src/control/services/settings.ts`, which is pure and directly tested in
`tests/unit/control/settings-privacy-truth.test.ts`. The tests ban the phrases
that would make it read like a check ("up to date", "checking", "update
available"), because the failure mode here is reassurance, not silence.

## How a user updates

Download the new build from the official CandidCue website and replace the app
in `/Applications`. Scripts, revisions, assets, settings, calibrations, the
database and the installed speech model all live in the application data
directory, not in the bundle, so replacing the app does not touch any of them.

The download origin is a legal placeholder (`@@LEGAL_WEBSITE_ORIGIN@@` — see
`legal/PLACEHOLDERS.md`). The UI deliberately does not hard-code a URL that
nobody has committed to yet; it names the official website in prose. When the
origin is resolved, the sentence can link to it — and that link needs a narrow
opener permission, not `opener:default` (see the capability-minimisation work).

## What was removed, and why it is not "reserved for later"

Until the 1.0 readiness pass, the tree carried a half-updater:

| Surface | What it was |
|---|---|
| `src-tauri/src/updates/mod.rs` | An `UpdateCheckCadence` enum defaulting to `Daily` |
| `GeneralSettings::update_check` | A persisted `"daily"` string nothing scheduled and nothing read |
| `check_for_update`, `install_update` | Registered commands that always returned `NOT_IMPLEMENTED` |
| Settings "Check for updates" | A button whose only possible answer was "not available in this build" |
| `UpdateCheckResult` | A frontend type for a result that could not occur |

Individually each was harmless. Together they described an application that
checks for updates daily, and the distance between that description and working
code was one plugin registration. A dormant contract of that shape is exactly
what gets switched on by someone who assumes the security and privacy work was
done when it was not: an updater needs a signing keypair, a pinned public key,
a pinned endpoint, signed artifacts, deferral during a live take, rollback on a
failed install, and a privacy disclosure that matches all of it.

Removing the settings field is backward-safe: `AppSettings` derives
`#[serde(default)]` and serde ignores unknown fields, so a settings row already
on disk carrying `updateCheck` still deserialises and simply drops it on the
next write.

## If an updater is ever added

Treat it as a feature with its own contract, not as filling in these blanks.
The minimum, from the 1.0 readiness review:

- `tauri-plugin-updater` with a pinned public key and endpoint;
- signed update artifacts produced by the same release workflow as the DMG;
- check/install state with cancellation, and **never** installing during a take;
- restart handling and a rollback policy for a failed install;
- tests for offline, timeout, invalid signature, downgrade, channel mismatch,
  interrupted install, and live-session deferral;
- an updated privacy disclosure and legal privacy-gate entry, because the app
  would then be making a network request the user did not start.
